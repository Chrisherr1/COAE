## 2.Filter-based Mitigations

Revolves around making whitelists and blacklists for inputs.

> Whitelists would be too restrictive for the user. So blacklists are the only real option.

Examples could include:
- Filtering the user prompt to remove malicious or harmful words and phrases
- Limiting the user prompt's length
- Checking similarities in the user prompt against known malicious prompts such as DAN

> Their Effectiveness is limited at best.

If a specific keyword is blocked, the attacker could just use a synonym or phrase the prompt in a different way.

> it should be used to complement other security measures.

---
## 3.Limiting the LLM's Access

Revolves around the idea of not giving the LLM access to anything sensitive in the first place.(Principle of least privilege).

> LLM should not do anything critical without human approval. Humans should always be in the loop so it can see if AI is making a mistake.

# LLM-Based Prompt Injection Mitigations

Traditional ways are inadequate.

These are better.

## Fine-Tuning Models

Its best to pick a model that best fits what you need it for, picking the right one can help resilience against prompt injection.

> You can then increase its robustness to prompt injection attacks, by fine tuning to the specific use case through additional training.

By training it for a specific use case, it narrows the scope of operation and what the user can prompt for.

---
## Adversarial Prompt Trainning 

> MOST EFFECTIVE AGAINST PROMPT INJECTION

You train the model to recognize common prompt injections/jailbreaks to help it identify and reject malcious prompts.

> The idea is the LLM exposed to the prompt before hand will be able to recognize and reject similar prompts.

> Common open source models like META's Lama and google gemma.
> already do this by default, so we typically don't have to do this training.

---
## Real-Time Detection Models

Guardrail LLMs:
2 types:

* Input guards
	* Works before input is fed to main LLM 
	* Error is returned if user prompt is flagged as malicious
* Output guards
	* Works on the output of the LLM
	* Scan the output for malicious or harmful content  and blocks the output.
	* Checks if it gave out sensitive information and blocks the output.
> They kinda act like validation and sanitization

> They require additional complexity and resources. Since the guardrail is basically an LLM, its like running 3 LLMs just for one response. (Input, LLM, Output).
> 
> Note: Guardrail LLMs are usually less complex than the main LLM.

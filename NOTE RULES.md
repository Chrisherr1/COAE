# NOTE RULES

Read this before opening a new module. Non-negotiable.

---

## The budget

| Scope | Hard cap |
|---|---|
| Per module page | **10 lines** |
| Per module | **1 note, 40 lines** |
| Whole path | **~400 lines** |

Current vault: 725 lines, and that covers roughly two pages of one module.
That is the problem this file exists to fix.

---

## The four line types

Every line must be one of these. If it is not, delete it.

- **A — Attack bridge.** Theory -> how it gets exploited.
  `embeddings = similarity vectors -> RAG poisoning`
- **Q — Open question.** Something you could not answer on the read.
  `Q: why does temperature change whether a jailbreak lands?`
- **C — Command / code.** Anything that actually ran. Never re-derive.
- **D — Definition.** Only if you need it AND cannot guess it. **Max 3 per module.**

Not on the list: definitions you could infer, worked examples, restated prose,
notation tables, anything the module page already says well.

---

## The mechanics

1. **Close the page before you write.** If the source is on screen, you will copy it.
   Read -> close -> write from memory. Cannot write it? You did not understand it.
   Re-read. That failure is worth more than a clean transcript.
2. **No copy-paste. Ever.** Your words or it does not go in the vault.
3. **5 minute timer per page.** Timer ends, note ends.
4. **One note per module.** Not per page. Append, do not create.

---

## The test

> Would I open this note *instead of* Ctrl-F-ing the module?

No -> do not write it. The module is not going anywhere.
For "what is a feature," the answer is always no.

---

## Weekly audit

Anything not reopened in a week: delete it.
A vault that only grows is a filing cabinet. It should shrink sometimes.
